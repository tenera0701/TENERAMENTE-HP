Webサイトの内容を、GoogleやAIは人間と同じようには読めません。構造化データは、機械に向けて「これは会社名です」「これは営業時間です」と明示的に伝えるための仕組み。AI検索の時代、その重要性は増す一方です。本記事では、JSON-LD での書き方を入門者向けに解説します。

📌 この記事の結論

構造化データは、Googleが推奨するJSON-LD形式で、まずOrganization・LocalBusiness・Article・FAQPageの4種類から始めるのが実用的です。検索のリッチリザルトだけでなく、AI検索に正確に引用されるための土台にもなります。

01構造化データとは？機械に渡す「名刺」

構造化データ（Structured Data）とは、ページの内容を検索エンジンやAIが理解できる形式で記述したデータのことです。共通の語彙として schema.org（スキーマ・ドット・オルグ）という規格が使われます。

たとえるなら、構造化データは**機械に渡す「名刺」**です。人間は「株式会社○○　名古屋市△△区…」という文字の並びから会社名と住所を読み分けられますが、機械には「どれが社名で、どれが住所か」の確証がありません。名刺のように「社名：○○」「住所：△△」とラベルつきで渡してあげる──それが構造化データの役割です。

02なぜAIO時代に重要なのか

これまで構造化データは、検索結果に星評価やFAQを表示させるリッチリザルトのための施策として語られてきました。しかし今は、もう一つの意味が加わっています。ChatGPTやPerplexity、GoogleのAI OverviewsといったAI検索に、正確に理解・引用してもらうための土台という役割です。

AIO（AI Optimization、AI最適化）の観点では、AIが「この会社は何者で、どこにあり、何を提供しているか」を誤解なく把握できることが重要です。構造化データは、その情報を曖昧さのない機械可読な形で提供します。文章の解釈に頼らせず、事実をそのまま渡せる──これが、AIO時代に構造化データが「基本装備」と言われる理由です。

03JSON-LDが推奨される理由：記述方式の比較

構造化データの書き方には主に3つの方式がありますが、Googleが推奨しているのはJSON-LDです。

方式 書き方 特徴
JSON-LD（推奨） <script>タグ内にJSONで記述 HTML本文と分離でき、追加・修正が容易
microdata HTMLタグに属性を付与 本文と一体で、修正時にHTML全体を触る必要がある
RDFa HTMLタグに属性を付与 表現力は高いが記述が複雑で、採用例は少なめ

JSON-LD（JavaScript Object Notation for Linked Data）の最大の利点は、既存のHTMLを書き換えずに、独立したブロックとして追加できること。導入も保守も圧倒的に楽なため、これから始めるならJSON-LD一択と考えて差し支えありません。

04中小企業サイトがまず入れるべき4種類

schema.orgには数百のタイプがありますが、全部を知る必要はありません。中小企業のサイトなら、まず次の4つで十分です。

Organization（組織）

会社名・ロゴ・URL・SNSアカウントなど、**「この会社は何者か」**を伝える基本情報。トップページに入れます。

LocalBusiness（店舗・地域ビジネス）

住所・電話番号・営業時間・地図座標など、実店舗の情報。店舗・クリニック・士業など来店型ビジネスでは、MEOとの相乗効果も期待できる最重要タイプです。

Article（記事）

ブログ記事のタイトル・公開日・更新日・著者を伝えます。情報の鮮度と出どころを明示できるため、AIの引用判断にも役立ちます。

FAQPage（よくある質問）

質問と回答のペアを構造化します。ユーザーの「聞き方」とAIへの「答え」を直接対応づけられる、AIOと特に相性のよいタイプです。

05JSON-LDの書き方：LocalBusinessの例

実際のコードを見てみましょう。以下は、地域ビジネスの基本的なJSON-LDの例です。<head>内または</body>直前に貼り付けます。

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "LocalBusiness",
  "name": "株式会社サンプル",
  "url": "https://example.com/",
  "telephone": "+81-52-000-0000",
  "address": {
    "@type": "PostalAddress",
    "addressRegion": "愛知県",
    "addressLocality": "名古屋市中区",
    "streetAddress": "丸の内1-2-3",
    "postalCode": "460-0002",
    "addressCountry": "JP"
  },
  "openingHours": "Mo-Fr 09:00-18:00"
}
</script>

ポイントは、@typeでタイプを宣言し、schema.orgで定義されたプロパティ名（name、addressなど）に値を入れていくだけ、というシンプルさです。ページに実際に表示されている情報と一致させることを忘れないでください。

!

実例

当社では、コーポレートサイト制作の標準工程に構造化データの実装を組み込んでいます。後から追加するより、制作時に「どのページに何のタイプを入れるか」を設計してしまうほうが、抜け漏れなく低コストで済むためです。

06検証方法：リッチリザルトテストで確認する

書いたJSON-LDが正しく認識されるかは、必ずツールで検証します。

  1. リッチリザルトテスト（Google公式）：URLまたはコードを貼り付けると、Googleがリッチリザルト対象として認識できるかを判定してくれます
  2. スキーママークアップ検証ツール（schema.org公式）：リッチリザルト対象外のタイプも含め、構文の妥当性を広く確認できます
  3. Google Search Console：公開後、サイト全体の構造化データのエラーや警告を継続的に監視できます

「書いて終わり」ではなく、公開前にテスト、公開後にSearch Consoleで監視という流れを習慣にしましょう。

07よくある間違い

!

注意：やってしまいがちなNG

①ページに表示されていない情報を構造化データにだけ書く（ガイドライン違反です）、②JSONのカンマ抜け・引用符ミスなどの構文エラーでまるごと無視される、③実態のない星評価（Rating）を入れて評価を偽る、④テンプレートのサンプル値を書き換え忘れてそのまま公開する。特に①と③は、手動対策（ペナルティ）の対象になり得ます。

構造化データは「盛る」ためのものではなく、事実を正確に伝えるためのものです。実際のページ内容と一致した、正直なマークアップだけが評価につながります。

08まとめ：小さく入れて、正しく検証する

構造化データは、専門家だけのものではありません。JSON-LDで、まず4種類（Organization / LocalBusiness / Article / FAQPage）を入れ、リッチリザルトテストで検証する──この小さな一歩が、Google検索とAI検索の両方に「正しく伝わるサイト」への土台になります。コピーして値を差し替えるだけでも始められますので、ぜひ自社サイトで試してみてください。

構造化データを入れると検索順位は上がりますか？
構造化データ自体は直接の順位要素ではない、というのがGoogleの公式見解です。ただし、リッチリザルトによる視認性の向上や、内容が正確に理解されることによる間接的な効果は期待できます。順位の裏技ではなく「正しく伝える施策」と捉えるのが適切です。
プログラミングの知識がなくても実装できますか？
JSON-LDはHTMLに1ブロック貼り付けるだけなので、サンプルの値を自社情報に差し替える形なら十分可能です。WordPressなどのCMSでは、プラグインで主要なタイプを自動出力する方法もあります。
どのページにどのタイプを入れればいいですか？
基本は、トップページにOrganization（店舗ならLocalBusiness）、ブログ記事にArticle、よくある質問のあるページにFAQPageです。1ページに複数のタイプを併記しても問題ありません。
